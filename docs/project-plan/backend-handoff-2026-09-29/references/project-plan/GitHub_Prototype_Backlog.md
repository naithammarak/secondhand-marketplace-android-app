# Prototype Backlog สำหรับเปิด GitHub Issues

ปรับปรุง: 5 กันยายน 2026

**ปรับข้อตกลงผลิตภัณฑ์ 26 กันยายน 2026:** ใช้ [FULFILLMENT-00](FULFILLMENT-00-delivery-proof-and-deadlines.md) สำหรับใบรับรอง หลักฐาน Courier, การยืนยันรับและเส้นตาย. ใบรับรองออกเมื่อผลตรวจ `PASS`/`MINOR_ISSUE`; ผู้ขนส่งถ่ายรูปและยืนยันส่งถึง; Buyer ยืนยัน **รับสินค้า** จึงปล่อยเงิน หรือปล่อยอัตโนมัติเมื่อครบ 72 ชั่วโมงจากหลักฐานส่งถึงโดยไม่มีรายงานว่าไม่ได้รับ. ข้อความเดิมที่เลื่อน timer ทั้งหมดหรือปล่อยเงินทันทีเมื่อเพียงส่งถึงถูกแทนที่เฉพาะประเด็นนี้. รหัส COURIER-01…03/TIMER-01 ด้านล่างเป็นงานเสนอใหม่ ยังไม่ใช่เลข Issue ใน GitHub.

แผนนี้ใช้ตามข้อตกลงล่าสุด: React Native + Expo, FastAPI, Supabase PostgreSQL และ Google Login ลดขอบเขตให้เน้นสาธิตการขายสำเร็จและการคืนสินค้า ใช้แทนลำดับการทำงานและขอบเขตใน Backlog รุ่นเดิม โดยรายละเอียดข้อกำหนดที่เปลี่ยนต้องปรับให้ตรงกับเอกสารส่งอาจารย์ด้วย

## 2. ขอบเขตที่ตกลงลด

เก็บ: Google Login, บทบาทผู้ใช้, การอนุมัติผู้ขายแบบง่าย, ลงสินค้าและรูป, รายการ/ค้นหาชื่อ/รายละเอียด, คำสั่งซื้อ, การจ่ายและขนส่งจำลอง, ผลตรวจ, QR สาธารณะ, การยืนยัน/ปฏิเสธ และการปล่อยเงิน/คืนเงินจำลอง

เลื่อนไปหลังส่ง: Push Notification, รีวิว, ตัวกรองซับซ้อน, โปรไฟล์ขั้นสูง, การส่งออก/ลบบัญชีด้วยตัวเอง, Wallet/ถอนเงินจริง และหน้าจอจัดการผู้ใช้ขั้นสูง. งานอัตโนมัติที่ยังอยู่ในต้นแบบคือยกเลิก Order ที่ไม่จ่ายใน 30 นาที, คืนเงินเมื่อผู้ขายไม่ส่งใน 3 วัน, เตือนงานตรวจเกิน 3 วันทำการ และปล่อยเงินเมื่อผู้ซื้อไม่ยืนยันรับภายใน 72 ชั่วโมงหลัง Courier ส่งถึงพร้อมหลักฐาน; **ไม่มี** การกดยอมรับผลตรวจแทนผู้ซื้ออัตโนมัติ

ใช้หน้าสถานะคำสั่งซื้อพร้อมปุ่ม Refresh และบัญชี COURIER ทดสอบที่มอบหมายเฉพาะ Shipment เพื่อถ่ายรูปและกดยืนยันส่งถึง; Inspector กดรับเข้าศูนย์แยกจาก Courier. ผู้ซื้อมีปุ่มยืนยันรับ/แจ้งว่ายังไม่ได้รับ; กรณีแจ้งไม่รับให้ Admin ตรวจหลักฐานก่อนปล่อยหรือคืนเงิน. ใช้ข้อมูลบุคคลสมมติในการ Demo ไม่เชื่อม Payment หรือ Shipping จริง

สิ่งที่ยังต้องทำ: ตรวจสิทธิ์ใน Backend, ตรวจข้อมูลสำคัญ, ไม่ทำรายการเงินซ้ำ, ไม่เปิดเผยข้อมูลส่วนตัวผ่าน QR และไม่เก็บ Secret ใน Git

## 3. วิธีนำไปใช้บน GitHub

1. สร้าง Issue หลักชื่อ `[Feature] Google Login` แล้วคัดลอกเป้าหมายจากหัวข้อ 5
2. เปิด Issue ย่อย LOGIN-01 ถึง LOGIN-08 ด้านล่าง ใช้ชื่อเรื่องและเนื้อหาคัดลอกได้ทันที
3. ใส่ผู้รับผิดชอบจริง และแทนรหัสงานที่ต้องรอด้วยลิงก์ GitHub Issue เมื่อสร้างแล้ว
4. เปิดงาน Feature ถัดไปเมื่อใกล้เริ่ม ไม่ต้องเปิดทุกงานเป็น In Progress พร้อมกัน

รหัส LOGIN-01 เป็นรหัสในแผน ไม่ใช่เลข Issue ที่ GitHub สร้างให้

ใช้ป้ายกำกับเท่าที่จำเป็น: `frontend`, `backend`, `database`, `qa`, `integration`

สถานะบนบอร์ด:

`พร้อมทำ → กำลังทำ → รอตรวจ → รอทดสอบ → เสร็จ`

เมื่อมีปัญหาที่ทำต่อไม่ได้ ให้เขียนใน Issue ว่ารออะไรและแจ้งคนที่ช่วยได้

งานแก้โค้ดใช้หนึ่ง Issue → หนึ่ง Branch → หนึ่ง Pull Request (PR: คำขอรวมโค้ดเข้า main) งานประชุม/ข้อตกลง/ทดสอบอย่างเดียวไม่จำเป็นต้องมี Branch หรือ PR

## 5. Feature แรก: Google Login

เป้าหมายรอบทดลองที่เป็นส่วนหนึ่งของงานจริง:

`กด Google Login บนมือถือ → Backend ตรวจตัวตน → อ่าน/สร้างผู้ใช้ใน Supabase PostgreSQL → แอปแสดงชื่อ`

ไม่สร้างโปรเจกต์ทดลองใหม่ ไม่ต้องทำ Test Message เพิ่ม แต่ใช้โครงและการเชื่อม Database ที่มีอยู่ต่อ

### LOGIN-01 — [Lead] ตกลงวิธี Google Login และข้อมูลผู้ใช้

**ผู้รับผิดชอบ:** Lead | **ผู้ช่วย:** BE, FE1, DB1 | **ต้องรอ:** ไม่มี

งาน:
- ตกลงว่าจะใช้ Google โดยตรงหรือผ่านบริการ Auth ใด และใครตรวจ/ออก Token (หลักฐานยืนยันตัวตนที่แอปแนบไปกับ API)
- ใช้วิธีเดียวสำหรับทั้งทีม ยังไม่ถือว่าการใช้ Supabase Database คือการเลือก Supabase Auth
- เขียนตัวอย่างข้อมูลที่ Mobile ส่ง และข้อมูลผู้ใช้/ข้อผิดพลาดที่ Backend ตอบไว้ใน Issue นี้
- กำหนดตัวระบุบัญชีที่เชื่อถือได้จากผู้ให้บริการ ห้ามใช้ชื่อแสดงเป็นตัวระบุบัญชี
- ตกลงวิธีเลือก Buyer/Seller ครั้งแรก การเตรียม Admin/Inspector และพฤติกรรมเมื่อ Token หมดอายุ
- บันทึกวิธีรันทดสอบบนมือถือให้ตรงกับวิธี Login ที่เลือก หากต้องใช้ Development Build ให้รวมการตั้งค่าไว้ใน LOGIN-02

เสร็จเมื่อ:
- [ ] FE, BE และ DB อ่านแล้วรู้ว่าต้องส่ง/เก็บข้อมูลอะไร
- [ ] มีตัวอย่าง Login สำเร็จและไม่สำเร็จ
- [ ] มีวิธีทดสอบบนมือถือจริงและผู้รับผิดชอบการตั้งค่าชัดเจน

### LOGIN-05 — [Backend] ตรวจ Login และอ่านข้อมูลผู้ใช้ของตัวเอง

**ผู้รับผิดชอบ:** BE | **ผู้ช่วย:** DB1, Lead | **ต้องรอ:** LOGIN-01, LOGIN-03; ทดสอบรวมกับ LOGIN-02

พื้นที่: `backend/app/`, `backend/tests/` แยกไฟล์ตามหน้าที่เมื่อจำเป็น

งาน:
- ตรวจหลักฐาน Google/Token ตามวิธีที่เลือก ไม่เชื่อข้อมูลตัวตนที่ Mobile ส่งมาโดยไม่ตรวจ
- สร้างผู้ใช้ใหม่หรืออ่านผู้ใช้เดิมโดยไม่สร้างซ้ำ
- รองรับขั้นตอนเลือก Buyer/Seller ครั้งแรกและสิทธิ์เจ้าหน้าที่ตามข้อตกลง
- ทำ `GET /me` เพื่ออ่านข้อมูลของผู้ที่ส่ง Token มา
- ตรวจสิทธิ์ที่ Backend และตอบข้อผิดพลาดเมื่อ Token ใช้ไม่ได้

เสร็จเมื่อ:
- [ ] Login ที่ถูกต้องอ่าน/สร้างผู้ใช้และเรียก `/me` ได้
- [ ] Login ซ้ำไม่สร้างผู้ใช้ซ้ำ
- [ ] ไม่มี Token หรือ Token ไม่ถูกต้องถูกปฏิเสธ
- [ ] ผู้ใช้ทั่วไปตั้งตัวเองเป็น Admin/Inspector ไม่ได้

## 10. คำสั่งหลัง Pull สำหรับแต่ละทีม

คำสั่งทั้งหมดใช้ใน Windows PowerShell และเริ่มจาก Repository จริงที่ `G:\SecondHandMarketPlace\SA-Project`

### ตรวจงานก่อน Pull - ทุกคนต้องทำ

```powershell
cd G:\SecondHandMarketPlace\SA-Project
git status
git switch main
git pull origin main
```

ถ้า `git status` แสดงไฟล์ที่แก้ไขอยู่ ให้หยุดก่อน อย่า Pull ทับ ให้ Commit งานใน Branch ของตัวเองหรือถาม Lead ว่าควรเก็บงานอย่างไร

`git pull` ดึงโค้ด แต่ไม่ได้ติดตั้ง Dependencies ให้ ต้องรันคำสั่งของทีมตัวเองด้านล่างหลัง Pull ครั้งแรก และรันใหม่เมื่อไฟล์ `package.json`, `package-lock.json` หรือ `requirements.txt` เปลี่ยน

### Frontend - React Native + Expo

ติดตั้ง Dependencies:

```powershell
cd G:\SecondHandMarketPlace\SA-Project\mobile
npm install
```

เปิดแอป:

```powershell
npx expo start
```

ถ้า Cache เก่าทำให้แอปแสดงผลผิดหรือเปิดไม่ได้:

```powershell
npx expo start --clear
```

ก่อนเปิด Pull Request ให้ตรวจเบื้องต้น:

```powershell
npm run lint
```

เมื่อเพิ่ม Package ใหม่ ให้ใช้ `npx expo install ชื่อ-package` เพื่อให้รุ่นเข้ากับ Expo แล้ว Commit ทั้ง `package.json` และ `package-lock.json` ห้าม Commit `node_modules/`

### Backend - FastAPI

ครั้งแรกหลัง Clone ให้สร้าง Python virtual environment และติดตั้ง Dependencies:

```powershell
cd G:\SecondHandMarketPlace\SA-Project\backend
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

ครั้งต่อไปหลัง Pull:

```powershell
cd G:\SecondHandMarketPlace\SA-Project\backend
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

ไฟล์ `.env` ต้องมีในเครื่องแต่ละคน แต่ไม่อยู่ใน Git ให้สร้างจากตัวอย่างเฉพาะครั้งแรก:

```powershell
Copy-Item .env.example .env
```

จากนั้นรับค่า `DATABASE_URL` จริงจากผู้ดูแล Database ผ่านช่องทางของทีมและใส่ใน `.env` ห้ามส่ง Secret ลง GitHub

เปิด API:

```powershell
python -m uvicorn app.main:app --reload
```

เปิด Swagger ที่ `http://127.0.0.1:8000/docs` และรัน Test ด้วย:

```powershell
python -m pytest
```

### Database - Supabase PostgreSQL + Alembic

Database Dev ใช้ Dependencies ชุดเดียวกับ Backend ไม่ต้องติดตั้ง PostgreSQL Server ในเครื่องเพื่อเชื่อม Supabase กลาง

ครั้งแรก:

```powershell
cd G:\SecondHandMarketPlace\SA-Project\backend
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
Copy-Item .env.example .env
```

ใส่ `DATABASE_URL` ที่ผู้ดูแลกำหนดใน `.env` แล้วตรวจ Migration ปัจจุบัน:

```powershell
python -m alembic current
python -m alembic history
```

ให้ Database Owner ที่ทีมกำหนดเพียงคนเดียวเป็นผู้รัน Migration ใหม่เข้า Supabase กลาง:

```powershell
python -m alembic upgrade head
```

Database คนที่สองตรวจไฟล์ Migration และผลใน Supabase Dashboard แล้วแจ้งทีมว่าใช้ Migration ถึง Revision ใด ไม่ต้องรันแข่งกันบน Database กลางเดียวกัน
