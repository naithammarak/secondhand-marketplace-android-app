## Contract question for Lead and cross-team review

**Deadline ordering:** #98 says a Buyer request that *arrives at the server* at/after the deadline returns 409; FINISH-spec v1 §3.1/§5 says the authoritative ordering point is the guarded DB write after acquiring the Order lock and re-reading the DB wall clock. Under lock contention, a request received before deadline but written after deadline differs between those rules. Proposed resolution: use DB write/commit eligibility as the linearization point, with a fresh database wall-clock read after lock acquisition. It yields deterministic races and matches exactly-once settlement; return `409 receipt_deadline_passed` if the Buyer action loses the boundary. Lead must record the accepted rule in #98 and update FINISH-spec/API copy before FINISH-03/TIMER-01 boundary implementation. Other established choices above need no new product decision.

## Physical-name and migration rule

Do not add `deliveries`, another `escrow`, another `certificate`, or a second Courier router. DB1 owns migrations that extend existing `shipments`/Courier proof/Order status constraints and reconciles `d8b7c4e2910a` with `e8b2c490a713`. DB2 owns FINISH settlement/command/history/resolution schema in a descendant revision after the candidate graph is known. FINISH-03 and FINISH-04 share one service owner/interface; no competing RELEASE and REFUND ledgers. Proposed columns such as `delivery_proof_confirmed_at` must first be mapped to actual `courier_delivered_at`; add aliases in API if useful, avoid redundant persisted timestamps.
