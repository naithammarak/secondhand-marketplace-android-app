# FINISH-01 / DB2 — settlement foundation (copy-ready v1)

**Objective:** Add constraints and durable records for one simulated RELEASE-or-REFUND per paid Order/Escrow. Do not implement shipment routes or financial decisions here. Product authority: [#98](https://github.com/naithammarak/secondhand-marketplace-android-app/issues/98), [decision register](FINISH-contract-decisions.md), [fixtures](FINISH-api-fixtures.md).

**Base and owner:** DB2 primary; DB1 owns the common Alembic lineage and shared Order/Shipment migrations. Start implementation only from L1's reviewed integrated candidate SHA and recheck PR heads, Git status, applied Alembic revisions and `AGENTS.md`. Use an isolated worktree/disposable PostgreSQL; never edit a234 or a shared DB.

**Inputs/gates:** G0 common graph, G1 exact `buyer_inspection_decisions`/Certificate FK mapping and G2 Shipment/proof/destination columns must be documented. If G2 Seller snapshot is still in progress, DB2 may complete a reviewed logical design and migration draft in an isolated branch, but must not publish a migration based on guessed shared fields/head. DB1 supplies the owner/sequence for `orders.status` CHECK and the partial unique outbound Shipment constraint; DB2 must not create a parallel Shipment/Proof/Certificate/Payment system.

**Implementation scope/files:** `backend/app/models/order.py` and `backend/migrations/versions/<new descendant>.py` for Order receipt deadline/source, report fields, status extensions, Escrow terminal status/time; add a single `OrderSettlement` model plus FINISH command, append-only status-history and audited delivery-resolution models under `backend/app/models/` if no equivalent candidate tables exist. Include them in model metadata/imports and read contracts. `order_settlements` needs unique `order_id` and unique `escrow_id`, immutable terminal kind `RELEASE|REFUND`, source/reason, currency/held amount and original seller/Buyer references. Use composite FK/unique tuples so settlement `(order_id, escrow_id, payment_id, held_amount)` points to the *same* Escrow/Payment/Order and held amount equals the Order snapshot; single-column FKs alone are insufficient. Keep one terminal unique key across both kinds; separate unique RELEASE and REFUND indexes would allow both. Use Decimal `NUMERIC(12,2)` and enforce RELEASE sum `seller_payout + commission + inspection + shipping = held_amount` with buyer refund zero, versus REFUND `buyer_refund = held_amount` and all seller/retained allocations zero. Add an immutability guard for the terminal row. FINISH commands need unique `(actor_scope, action, resource_type, resource_id, key)`, request hash and committed result reference; history needs an immutable event/operation reference; Admin resolution is unique per Order and includes Admin, reason, scoped evidence refs and timestamp. Receipt report, Admin resolution and history have stable IDs and per-Order uniqueness where appropriate. Keep historical `Payment`/`Receipt` rows unchanged. Map existing `Shipment.courier_delivered_at` rather than adding a redundant timestamp.

**Acceptance:** On fresh and supported predecessor disposable PostgreSQL DBs, one expected Alembic head; upgrade preserves paid/unpaid Orders and existing proof/certificate/decision rows; direct invalid writes fail (duplicate/opposite settlement, wrong Order/Escrow/Payment tuple, negative allocation, mismatched total, contradictory receipt/report fields); two independent connections racing on one Order cannot insert opposing settlements; safe downgrade refuses populated incompatible records. Check RLS for new public tables. `git diff --check` and relevant model/migration tests pass. Record exact candidate SHA, migration revision, commands, DB names as disposable, constraints, and rollback limits.

**Stop/escalate:** Stop before migration publication if L1 graph/history or shared-column ownership is unresolved, if the Seller snapshot is silently synthesized, or if financial invariant cannot be expressed/tested.
