## 1. ผลลัพธ์ที่ต้องการ

```
ตรวจผ่าน → ออกใบรับรองทันที → ผู้ซื้อยอมรับผลตรวจ → ส่งไปผู้ซื้อ
→ ผู้ขนส่งถ่ายรูปและกดยืนยันว่าส่งถึง → ผู้ซื้อยืนยันรับ → ปล่อยเงินจำลอง
                                             ↘ ไม่ตอบภายใน 72 ชั่วโมง → ปล่อยเงินอัตโนมัติ
                                             ↘ แจ้งว่ายังไม่ได้รับ → พักเงิน รอเจ้าหน้าที่ตรวจ
```

“ยอมรับผลตรวจ” ใน CERT-04 กับ “ยืนยันว่าได้รับสินค้า” ใน FINISH เป็น **คนละเหตุการณ์และคนละข้อมูล**. การยอมรับผลตรวจไม่ปล่อยเงิน. ใบรับรองเป็นหลักฐานผลตรวจ ไม่ยืนยันการจัดส่ง ความเป็นเจ้าของ หรือการปล่อยเงิน. ถ้าผลตรวจไม่ผ่าน/ผู้ซื้อปฏิเสธผลตรวจ ให้ส่งคืนผู้ขายพร้อมรูปหลักฐานตอนส่งคืน และคืนเงินจำลองเต็มจำนวนหลังส่งคืนสำเร็จ.

ต้นแบบยังใช้การชำระเงินและขนส่งจำลอง แต่ข้อมูล Order, รูปหลักฐาน, เวลาจาก Server, การตัดสินใจของผู้ซื้อ และรายการเงินต้องบันทึกจริงในฐานทดสอบ. ไม่ใช้การเปลี่ยนสถานะจาก Mobile อย่างเดียว.

## 2. กติกาที่ตัดสินแล้ว

| เรื่อง | ข้อตกลง |
|---|---|
| ผลตรวจที่ถือว่า “ผ่าน” | `PASS` หรือ `MINOR_ISSUE`; กรณี `MINOR_ISSUE` ใบรับรองต้องบอกข้อสังเกตตามจริง ไม่แสดงว่าเป็น PASS ล้วน |
| ออกใบรับรอง | บันทึกผลตรวจและ Certificate ใน PostgreSQL transaction เดียวกันก่อนตอบสำเร็จ หนึ่งใบต่อ Order/ผลตรวจ; `NOT_AS_DESCRIBED`/`FAKE` ไม่มีใบรับรอง |
| หลังผลตรวจผ่าน | ผู้ซื้อกด `CONFIRM`/`REJECT` ผลตรวจได้ครั้งเดียว. ยังไม่มีการยืนยันผลตรวจแทนผู้ซื้ออัตโนมัติ; หากไม่ตอบ 72 ชั่วโมงให้แจ้งเจ้าหน้าที่ติดตาม แต่ Order ยังรอและเงินยังพัก |
| ใครยืนยันการส่งถึง | บัญชี `COURIER` สำหรับต้นแบบ ซึ่งเจ้าหน้าที่สร้างและมอบหมายให้ Shipment เฉพาะรายการ; ไม่ให้ Buyer/Seller ตั้งตนเป็น Courier |
| จุดส่งถึง | ทุก leg (`TO_CENTER`, `TO_BUYER`, `TO_SELLER`) ต้องมีรูปและการกดยืนยันของ Courier; ศูนย์ตรวจยืนยันรับเข้าศูนย์แยกอีกครั้ง. การส่งถึงผู้ซื้อเป็นจุดเริ่มนับ 72 ชั่วโมง |
| รูปหลักฐานส่งถึง | 1–3 ภาพ JPEG/PNG ภาพนิ่ง, ภาพละไม่เกิน 5 MiB, เก็บ private; ตรวจชนิดไฟล์จากเนื้อหา/ขนาดจริง; เก็บ hash, เวลา Server, Courier และ shipment; ไม่เผยแพร่ใน QR/รายการสาธารณะ |
| ผู้ซื้อยืนยันรับ | หลัง Courier ส่งถึงผู้ซื้อแล้วเท่านั้น. ผู้ซื้อเจ้าของ Order กดรับหนึ่งครั้ง; ระบบปล่อยเงินจำลองใน transaction เดียวกับการปิดรายการ |
| ไม่ตอบภายใน 3 วัน | ใช้ **72 ชั่วโมงเต็ม** จาก `delivery_proof_confirmed_at` ที่ Server บันทึก ไม่ใช่ 3 วันตามปฏิทินหรือเริ่มจากผลตรวจ. Job ตรวจเมื่อ `now >= receipt_deadline_at` และปิดรายการพร้อมปล่อยเงินให้ผู้ขายเพียงครั้งเดียว |
| แจ้งว่ายังไม่ได้รับ | ผู้ซื้อกดก่อนครบ 72 ชั่วโมงแล้วหยุดการปล่อยอัตโนมัติทันที. เงินคง `HELD`; Admin ตรวจรูปและหลักฐานการส่งก่อนตัดสินปล่อย/คืนเงิน พร้อมเหตุผลและ audit. ไม่ต้องสร้างระบบข้อพิพาทเต็มรูปแบบในต้นแบบ |
| รูป/การยืนยันหาย | ไม่เป็น `DELIVERED`, ไม่เริ่มเวลา 72 ชั่วโมง, ไม่ปล่อยเงิน. ตอนยืนยันและก่อน auto-release ต้องตรวจว่า object ของรูปหลักฐานยังอ่านได้; Storage ใช้งานไม่ได้ให้คงเงิน `HELD` และ retry/แจ้งทีม. Courier แก้/ส่งใหม่ตามกติกา retry; อัปโหลดที่ค้างต้องมี cleanup |
| ส่งคืนผู้ขาย | Courier ต้องถ่ายรูป/กดยืนยันว่าส่งคืนถึงผู้ขาย; ไม่ต้องรอ Seller ยืนยันเพื่อคืนเงินให้ Buyer. คืนเต็มยอดเดิมเพียงครั้งเดียวหลังหลักฐานส่งคืนสำเร็จ |
| ค่าธรรมเนียมจำลอง | ใช้ค่าที่ code ปัจจุบันมีอยู่: ค่าขนส่งผู้ซื้อ 50.00 บาท, ค่าตรวจผู้ซื้อ 100.00 บาท, ค่าคอมมิชชัน 5% ของราคาสินค้าหักจากผู้ขาย. ไม่หักค่าตรวจจากผู้ขายซ้ำ; ไม่คิดค่าขนส่งคืนเพิ่มในต้นแบบ |
| คืนเงิน | คืน `order.total_amount` เต็มจำนวนจาก snapshot เดิมเมื่อผลตรวจไม่ผ่าน ผู้ซื้อ `REJECT` ผลตรวจ หรือผู้ขายไม่ส่งภายในกำหนด. ไม่ลบประวัติ Payment/Receipt เดิม |
| สินค้าตรวจไม่ผ่าน/คืนแล้ว | คงไม่อยู่ในรายการขายสาธารณะ; ไม่ relist อัตโนมัติ. สินค้าขายสำเร็จเป็น `SOLD` |

บัญชี `COURIER` เป็นบัญชีปฏิบัติงานจำกัดสิทธิ์ **เพิ่มจาก 4 บทบาทตลาดเดิม** เฉพาะการสาธิตขนส่ง ไม่ใช่ช่องให้สมัครจาก Mobile. ต้องปรับ `UserRole`/migration/auth guard และเอกสาร SRS ที่ระบุ 4 กลุ่มก่อนเปิดใช้งานจริง. ถ้าทีมจะเชื่อมผู้ให้บริการขนส่งภายนอกภายหลัง ให้ใช้ interface เดียวกันโดยยังตรวจหลักฐานและสิทธิ์ฝั่ง Server.

## 3. ข้อมูลและสิทธิ์

### 3.1 แบบข้อมูลขั้นต่ำที่เสนอ

- `shipments`: ต่อจาก INSPECT-01; เพิ่ม `leg=TO_BUYER/TO_SELLER`, `assigned_courier_id`, `delivered_at`, `delivery_proof_confirmed_at`, `recipient_type`, `status`. `TO_CENTER` ต้องใช้กติกาหลักฐานเดียวกัน. Unique `(order_id, leg)`; หนึ่ง Order มี leg ขาออกจากศูนย์ได้เพียงทิศเดียวภายใต้ Order lock.
- `shipment_delivery_proofs`: `id`, `shipment_id` FK, `object_key` private, `sha256`, `mime_type`, `size_bytes`, `uploaded_by`, `uploaded_at`, `confirmed_at`; เชื่อมรูป 1–3 ภาพกับการยืนยันหนึ่งครั้ง. รูปและ metadata หลังยืนยันแก้/ลบไม่ได้ผ่าน API ปกติ.
- `receipt_deadline_at`: เก็บที่ Order หรือ delivery confirmation อย่างใดอย่างหนึ่งซึ่งอ่านอย่างคงที่; เป็น UTC, เท่ากับ `delivery_proof_confirmed_at + 72 hours`. เก็บ `receipt_confirmed_at`, `receipt_confirmation_source=BUYER/AUTO`, `delivery_reported_missing_at` และเหตุผลที่ต้องพักเงิน.
- `order_settlements`: หนึ่ง terminal settlement ต่อ Order และ Escrow ใช้ unique/FK ระดับฐานข้อมูล, `kind=RELEASE/REFUND`, จำนวนเงินและการจัดสรร, key/actor, timestamp. ห้ามมี RELEASE กับ REFUND คู่กัน. การเปลี่ยน Order/Escrow/Product/ledger ต้อง atomic.
- `order_status_history`: เก็บ actor, ก่อน/หลัง, เวลา และเหตุการณ์เช่น Courier proof, Buyer receipt, auto-release, missing-delivery hold โดยไม่เขียนทับประวัติเดิม.

`COURIER` อ่านได้เฉพาะข้อมูลที่จำเป็นของ Shipment ที่มอบหมายและอัปโหลด/ยืนยันได้เฉพาะรายการนั้น; ไม่อ่านผลตรวจ รูปบัตร ข้อมูลจ่ายเงิน หรือ Order อื่น. Buyer อ่านรูปส่งถึงของ Order ตนได้ผ่าน API ที่ตรวจสิทธิ์; Seller/Inspector/Admin เห็นตามหน้าที่เท่านั้น. รูปทั้งหมดอยู่ใน private storage, ไม่มี public/signed URL อายุยาวใน QR หรือ log. Admin เปิดข้อมูล/หลักฐานกรณีแจ้งไม่รับต้องมีเหตุผลและ audit.

### 3.2 สัญญา API ที่เสนอ

ชื่อ path ปรับได้เมื่อ FE/BE ตกลง แต่พฤติกรรมต้องคงเดิม. ทุก mutation ใช้ Bearer token, `Idempotency-Key` ตาม Order contract, เวลา Server และ transaction/row lock; ไม่รับ `user_id`, ยอดเงิน หรือ status ปลายทางจาก client.

| Endpoint | ผู้เรียก | กติกา |
|---|---|---|
| `POST /admin/shipments/{id}/assign-courier` | Admin | มอบหมายบัญชี Courier ที่ ACTIVE ให้ leg นั้นก่อนยืนยันส่งถึง; เปลี่ยนผู้รับงานได้เฉพาะก่อนมีรูปอัปโหลด พร้อมเหตุผล/audit; Courier มอบหมายตนเองไม่ได้ |
| `POST /shipments/{id}/delivery-proofs` | Courier ที่ได้รับมอบหมาย | อัปโหลดรูป 1–3 ภาพและ metadata ที่ปลอดภัย; ยังไม่เปลี่ยนเป็น DELIVERED |
| `POST /shipments/{id}/confirm-delivery` | Courier คนเดิม | ต้องมีรูปครบ; บันทึก proof confirmation + `delivered_at` ครั้งเดียว. `TO_BUYER` คำนวณ deadline 72 ชั่วโมง, `TO_SELLER` เปิดทาง refund, `TO_CENTER` รอ Inspector รับ |
| `POST /shipments/{id}/receive-at-center` | Inspector | รับสินค้าที่มี proof เข้าศูนย์, บันทึกผู้รับ/เวลา; ไม่มีสิทธิ์สร้าง proof แทน Courier |
| `GET /orders/{id}/delivery` | Buyer/Seller ที่เกี่ยวข้อง | สถานะ leg, เวลาส่งถึง/deadline, รูปที่มีสิทธิ์, `can_confirm_receipt`, `can_report_missing` และสถานะเงิน; ไม่มีข้อมูลผู้อื่น |
| `POST /orders/{id}/confirm-receipt` | Buyer เจ้าของ | ต้องเป็น TO_BUYER ที่ Courier ยืนยันส่งถึง, ยังไม่แจ้งไม่รับ, `now < receipt_deadline_at` และ Escrow ยัง HELD; บันทึก `BUYER` และ release/COMPLETED atomic |
| `POST /orders/{id}/report-not-received` | Buyer เจ้าของ | ก่อน deadline, เก็บเหตุผลอย่างน้อย 10 ตัวอักษร; lock order และหยุด auto-release; ไม่คืนเงินทันที |
| `POST /admin/orders/{id}/resolve-delivery` | Admin | หลังรายงานไม่รับ; บันทึกเหตุผล/หลักฐานและ `RELEASE` หรือ `REFUND` ผ่าน service เดียวกับ FINISH; audit ทุกครั้ง; ไม่เลือกจำนวนเงินเอง |

Courier upload และ confirm แยกกันเพื่อให้ retry ภาพที่ล้มเหลวได้; proof ที่ยังไม่กดยืนยันไม่มีผลต่อเวลาหรือเงิน. คำขอซ้ำ key เดิม/body เดิมคืนผลเดิม, key เดิม/body ต่างตอบ 409, คำขอแข่งกันมีผู้ชนะหนึ่งรายการ. ภาพที่อัปโหลดแล้วแต่ DB commit outcome ไม่แน่ชัดต้อง reconcile ก่อน cleanup เพื่อไม่ลบหลักฐานที่มีการอ้างอิง.

## 4. งานอัตโนมัติ

ใช้ worker/scheduler ที่รันจริงแม้ไม่มีใครเรียก API, สแกนเป็นชุดเล็ก **ทุก 5 นาที** และรันย้อนหลังหลัง restart. ทั้ง worker และ API ใช้ operation เดียวกันภายใต้ Order row lock และ unique settlement. การปล่อยเงินต้องตรวจ deadline, Courier proof ที่อ่าน object ได้, ไม่มีรายงานไม่รับ, escrow `HELD`, Payment สำเร็จ, ไม่มี settlement และไม่มีสถานะคืนสินค้าอีกครั้งก่อน commit. ถ้า private Storage ล่มให้ retry พร้อมแจ้งทีม โดยไม่แสดงว่าเงินถูกปล่อยแล้ว.

| กำหนด | เวลาเริ่ม | เมื่อครบกำหนด | สถานะเงิน |
|---|---|---|---|
| จ่ายเงิน 30 นาที | `orders.created_at` | หากยังไม่จ่าย ให้ยกเลิกด้วย reason `EXPIRED` และปลดจอง; รวมงาน PR #92 หลัง INT-01 | ไม่มี Escrow ให้คืน |
| ผู้ขายส่งเข้าศูนย์ 3 วัน | `orders.paid_at` | หากยังไม่มีคำสั่ง Seller `ship-to-center` ที่บันทึก `shipped_at` และ Shipment `TO_CENTER` จริง ให้คืนเงินเต็มจำนวนและไม่ relist อัตโนมัติ; ถ้า refund ล้มเหลวคงสถานะรอ retry | คืนเต็มเมื่อ commit สำเร็จ |
| ศูนย์ตรวจออกผล 3 วันทำการ | Inspector รับเข้าศูนย์ | แจ้งเตือน/ยกระดับให้ Admin ตามปฏิทินวันทำการที่ทีมกำหนด; **ไม่สร้างผลตรวจปลอม** | คง HELD |
| ผู้ซื้ออ่านผลตรวจ 72 ชั่วโมง | `inspected_at` | เตือน/ยกระดับให้ Admin ติดตาม; **ไม่ถือว่ายอมรับผลตรวจโดยอัตโนมัติ** | คง HELD |
| ผู้ซื้อยืนยันรับ 72 ชั่วโมง | `delivery_proof_confirmed_at` ของ `TO_BUYER` | ถ้าไม่มี `report-not-received`, ปล่อยเงินและปิด Order แบบ `AUTO`; ถ้ามีรายงาน หยุดจน Admin ตัดสิน | RELEASED หรือคง HELD ตามเหตุการณ์ |

วันทำการของศูนย์ตรวจต้องมี timezone และปฏิทินวันหยุดที่กำหนดใน configuration; สำหรับต้นแบบให้ใช้ `Asia/Bangkok`, จันทร์–ศุกร์ ไม่รวมวันหยุดพิเศษจนกว่าจะมีตารางวันหยุด. เก็บเวลาจริง UTC. ทุก job มี log จำนวนงานที่พบ/สำเร็จ/ล้มเหลวและแจ้งทีมเมื่อค้างเกินรอบ; ห้ามแก้สถานะในแอปด้วย timer ฝั่ง client.

กรณี Buyer `confirm-receipt`/`report-not-received` กับ job ครบ 72 ชั่วโมงชนกัน ให้ล็อก Order เดียวกัน. ก่อน deadline ผู้ซื้อยืนยันรับหรือรายงานว่าไม่รับได้; ตั้งแต่ `receipt_deadline_at` เป็นต้นไปให้ worker เป็นผู้ปิดแบบ `AUTO` เท่านั้น. คำขอ Buyer ที่ถึง Server หลัง deadline ได้ 409 พร้อมสถานะล่าสุด; คำขอที่ commit ก่อน deadline ต้องชนะและกัน worker ไม่ให้ทำซ้ำ. งานค้างเพราะ worker ล่มต้องยัง `HELD` และแสดงว่ารอปล่อยเงิน; เมื่อ worker กลับมาทำต่อได้เพียงครั้งเดียว. การแจ้งส่งเข้าศูนย์ต้องมี Shipment/เวลาส่งที่บันทึกสำเร็จภายใน 3 วัน; Shipment ที่ค้างระหว่างทางเกิน 3 วันหลัง `shipped_at` ให้แจ้ง Admin ติดตาม โดยยังพักเงินและไม่สร้างหลักฐานส่งถึงแทน Courier.

## 5. เงินจำลองและเงื่อนไขจบรายการ

ใช้ snapshot ใน Order ที่มีอยู่ ไม่คำนวณใหม่จากราคาสินค้า. เงินทุกช่องใช้ `Decimal/NUMERIC`, JSON เป็น string. ตัวอย่างสินค้าราคา 1,200.00 บาท:

| รายการ | จำนวน |
|---|---:|
| ราคาสินค้า | 1,200.00 |
| ผู้ซื้อจ่ายค่าขนส่ง + ตรวจ | 50.00 + 100.00 |
| ผู้ซื้อจ่ายรวม/เงินพัก | **1,350.00** |
| ค่าคอมมิชชัน 5% จากราคาสินค้า | 60.00 |
| ผู้ขายได้รับจากการขายสำเร็จ | **1,140.00** |
| การจัดสรรที่เหลือให้ค่าคอมมิชชัน/ตรวจ/ขนส่งจำลอง | 60.00 + 100.00 + 50.00 |
| หากคืนเงิน | ผู้ซื้อได้เงินคืน **1,350.00**; ผู้ขายไม่ได้รับ 1,140.00 |

ยอด `1,140 + 60 + 100 + 50 = 1,350` ต้องเท่ากับ Escrow ที่พัก. ไม่มีเงินจริงเข้าธนาคาร/ผู้ให้บริการใน Prototype. FINISH-03/04 ต้องใช้ ledger/service เดียวที่บังคับ exactly-once และมี transaction rollback test. Receipt เดิมยังอยู่ พร้อมรายการคืนเงินแยก ไม่ลบ Payment ที่เคยสำเร็จ.
