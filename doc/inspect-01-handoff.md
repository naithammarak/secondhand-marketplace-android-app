# INSPECT-01 database handoff

Implemented against [INSPECT-00 #54](https://github.com/naithammarak/secondhand-marketplace-android-app/issues/54), Lead v1 updated 2026-09-23 14:49:49 UTC, and [INSPECT-01 #56](https://github.com/naithammarak/secondhand-marketplace-android-app/issues/56). #54 remains open for team review. Recheck its revision before merge and adjust this migration if the contract changes.

Migration `f3c1a09d8b56` follows `9446ec1a2c5d`. It adds `shipments`, `inspections`, `inspection_evidence`, `inspection_result_evidence`, and `inspection_idempotency`; expands `ck_orders_status` to the four Inspect states while preserving both old states; and adds queue indexes. New tables have RLS enabled with no anon/authenticated policy. The existing Order, Payment, Escrow and Receipt tables are preserved.

The database enforces one inbound shipment and inspection per Order, valid shipment/result values, complete receipt and final-result fields, private evidence metadata limits, same-inspection evidence links, and scoped idempotency keys. A trigger rejects overwriting/deleting a final result and modifying/deleting selected evidence links. The application must still lock the Order row, verify payment plus HELD escrow, roles and ownership, inspect state transitions, actual image bytes, selected image count 1–5, and make result/evidence/Certificate/status/idempotency one transaction. A positive result must never be reported successful without its Certificate.

BE needs to extend `OrderStatus`/serializers for the four new states before endpoints write them. In particular, the Seller `order_view` currently exposes `shipping_address` only in `WAITING_SELLER_SHIP`; review the right scope after `SHIPPING_TO_CENTER`. FE must update its Order status decoder and labels. CERT-01 must use `inspections(id, order_id)` as the parent key and enforce its own uniqueness/atomic gate. This change does not expose Inspect HTTP APIs or write storage files.

Run the PostgreSQL migration suite using a dedicated empty local database as documented in `backend/test-data/README.md`. It checks preexisting Order data through upgrade/downgrade/upgrade, schema/RLS/indexes, constraints, repeatable fixtures and simultaneous writes. Downgrade refuses any Inspect rows or Order with an Inspect status, so a production rollback needs an explicit data migration and backup plan. DB1/DB2 should record staging database revision, backup/restore readiness and the named central database operator before rollout; this handoff does not nominate that person.

Local verification on 2026-09-23: Alembic reports one head (`f3c1a09d8b56`); offline PostgreSQL SQL renders successfully; backend pytest reports 346 passed and 39 skipped. The INSPECT-01 PostgreSQL tests are among the skipped cases because `INSPECT_TEST_DATABASE_URL` is unavailable here. They must pass on a separate database before this work is certified for merge/deployment. No migration or seed was applied to a shared database.
