# INSPECT-01 database handoff

Implemented against [INSPECT-00 #54](https://github.com/naithammarak/secondhand-marketplace-android-app/issues/54), including the Lead decision dated 26 September 2026, and [INSPECT-01 #56](https://github.com/naithammarak/secondhand-marketplace-android-app/issues/56). The team confirms that decision as the current contract; the older issue body still describes the previous draft.

Migration `f3c1a09d8b56` follows ORDER-08/09 revision `c93b7e5a1d84` from PR #92. It adds `shipments`, `shipment_delivery_proofs`, `inspections`, `inspection_evidence`, `inspection_result_evidence`, and `inspection_idempotency`; expands `ck_orders_status` to the four Inspect states while preserving `WAITING_PAYMENT`, `WAITING_SELLER_SHIP`, and `CANCELLED`; and adds queue indexes. New tables have RLS enabled with no anon/authenticated policy. Existing Order, Payment, Escrow and Receipt rows are preserved.

The database enforces one shipment per Order and leg, one inspection per Order, a `COURIER` role, assigned Courier proof ownership, private JPEG/PNG proof metadata (1–3 images, at most 5 MiB each), and confirmed Courier delivery before Inspector receipt. Proof and assignment changes are rejected after confirmation. `TO_BUYER` and `TO_SELLER` shipment legs are stored for FINISH; their Courier confirmation does not record an Inspector receipt. Triggers also protect final inspection results and evidence. The application must lock the Order row, authorize Admin assignment and active Courier actions, verify actual image bytes and private object access, and confirm TO_CENTER delivery before Inspector receives. INSPECT-03/CERT must still make result/evidence/Certificate/status/idempotency one transaction.

The Order API schema and list/detail serializers read all four new Inspect states and `CANCELLED`. BE/Courier-02 must add protected assignment, image upload and delivery confirmation endpoints. INSPECT-02 must refuse Inspector receipt until `courier_delivered_at` and 1–3 usable private proofs exist. FE must update status labels and Courier screens. CERT-01 must use `inspections(id, order_id)` as the parent key and enforce its own uniqueness/atomic gate. This change does not expose Courier/Inspect HTTP APIs or write storage files.

Run the PostgreSQL migration suite using a dedicated empty local database as documented in `backend/test-data/README.md`. It checks preexisting paid and CANCELLED Orders through upgrade/downgrade/upgrade, schema/RLS/indexes, Courier proof guards, repeatable fixtures and simultaneous writes. Downgrade refuses any Inspect/Courier rows or Order with an Inspect status. The shared Supabase database reports untracked revision `ab2409240001`; find and reconcile that migration before deploying this stack. This handoff does not nominate the central database operator.

Local verification on 2026-09-23: Alembic reports one head (`f3c1a09d8b56`); offline PostgreSQL SQL renders successfully. On an isolated PostgreSQL 17.11 cluster bound to `127.0.0.1`, all 11 INSPECT-01 integration tests passed, including migration, constraints, RLS, repeatable seed data, final-evidence guards and concurrent writes. The full backend suite with that cluster enabled passed 361 tests and skipped 31 unrelated cases. No migration or seed was applied to a shared database. INSPECT-00 #54 approval and the DB1/DB2 rollout gates above remain open before merge/deployment.

Review follow-up on 2026-09-25: all 11 INSPECT-01 tests passed on a separate local PostgreSQL 18 cluster with non-superuser `anon` and `authenticated` roles granted table privileges. Tests now verify that a finalized inspection cannot move to another Order, all evidence is frozen after finalization, and an existing paid Order retains its Payment, Escrow and Receipt through upgrade/downgrade/upgrade. The backend suite without a PostgreSQL URL passed 349 tests and skipped 43, including the PostgreSQL-only checks. No shared database was changed.

The [contract comparison and rollout evidence worksheet](inspect-01-acceptance-rollout.md) records what matches draft #54, the four result mappings, staging/backup/restore steps and the named confirmations still required from Lead and DB1/DB2.
