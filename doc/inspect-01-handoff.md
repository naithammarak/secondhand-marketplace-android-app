# INSPECT-01 database handoff

Implemented against [INSPECT-00 #54](https://github.com/naithammarak/secondhand-marketplace-android-app/issues/54), Lead v1 updated 2026-09-23 14:49:49 UTC, and [INSPECT-01 #56](https://github.com/naithammarak/secondhand-marketplace-android-app/issues/56). #54 remains open for team review. Recheck its revision before merge and adjust this migration if the contract changes.

Migration `f3c1a09d8b56` follows `9446ec1a2c5d`. It adds `shipments`, `inspections`, `inspection_evidence`, `inspection_result_evidence`, and `inspection_idempotency`; expands `ck_orders_status` to the four Inspect states while preserving both old states; and adds queue indexes. New tables have RLS enabled with no anon/authenticated policy. The existing Order, Payment, Escrow and Receipt tables are preserved.

The database enforces one inbound shipment and inspection per Order, valid shipment/result values, complete receipt and final-result fields, private evidence metadata limits, same-inspection evidence links, and scoped idempotency keys. Triggers reject overwriting/deleting a final result, late result-evidence links and evidence uploads, mutation of selected evidence, and moves into a finalized inspection. The application must still lock the Order row, verify payment plus HELD escrow, roles and ownership, inspect state transitions, actual image bytes, selected image count 1–5, and make result/evidence/Certificate/status/idempotency one transaction. A positive result must never be reported successful without its Certificate.

The Order API schema and list/detail serializers now read all four new states. In particular, the Seller `order_view` currently exposes `shipping_address` only in `WAITING_SELLER_SHIP`; BE must review the right scope after `SHIPPING_TO_CENTER`. FE must update its Order status decoder and labels. CERT-01 must use `inspections(id, order_id)` as the parent key and enforce its own uniqueness/atomic gate. This change does not expose Inspect HTTP APIs or write storage files.

Run the PostgreSQL migration suite using a dedicated empty local database as documented in `backend/test-data/README.md`. It checks preexisting Order data through upgrade/downgrade/upgrade, schema/RLS/indexes, constraints, repeatable fixtures and simultaneous writes. Downgrade refuses any Inspect rows or Order with an Inspect status, so a production rollback needs an explicit data migration and backup plan. DB1/DB2 should record staging database revision, backup/restore readiness and the named central database operator before rollout; this handoff does not nominate that person.

Local verification on 2026-09-23: Alembic reports one head (`f3c1a09d8b56`); offline PostgreSQL SQL renders successfully. On an isolated PostgreSQL 17.11 cluster bound to `127.0.0.1`, all 11 INSPECT-01 integration tests passed, including migration, constraints, RLS, repeatable seed data, final-evidence guards and concurrent writes. The full backend suite with that cluster enabled passed 361 tests and skipped 31 unrelated cases. No migration or seed was applied to a shared database. INSPECT-00 #54 approval and the DB1/DB2 rollout gates above remain open before merge/deployment.
