# รอบถัดไป — มุมมอง Order ของ Inspector (ส่งต่อจาก ORDER-09)

> เอกสารนี้มีไว้เพื่อ **ไม่ต้องถกซ้ำ** ว่าทำไมงาน Inspector ไม่อยู่ในรอบนี้
> และเพื่อให้รอบถัดไปเริ่มจากสิ่งที่ SRS ตอบไว้แล้ว ไม่ใช่เริ่มจากศูนย์
>
> **ห้ามสร้างตารางการตรวจสอบ ตารางการจัดส่ง หรือ Endpoint ของ Inspector ล่วงหน้า**
> จนกว่ารอบนั้นจะเริ่มจริง เพราะยังไม่มีข้อสรุปเรื่องสิทธิ์และจะกลายเป็นโค้ดตายที่ต้องรื้อ
>
> อ้างอิง: Software Requirements Specification เวอร์ชัน 1.5 (ไฟล์ SRS ไม่ได้อยู่ใน repo นี้
> เอกสารนี้จึงอ้างเลขข้อเพื่อให้ไปเปิดต้นฉบับ ไม่ได้คัดลอกเนื้อหามาทั้งหมด)

## 1. ทำไมไม่อยู่ในรอบนี้ — ติดที่ขอบเขต ไม่ใช่ติดที่โจทย์

เหตุผลเดิมที่เคยบันทึกไว้ว่า "ยังไม่มีโจทย์ ในระบบมีแค่ชื่อบทบาท" **ไม่ถูกต้อง**
SRS กำหนดงานของ Inspector ไว้แล้วใน **FR-15 ถึง FR-18** และในกระบวนการทำงานหลัก **ขั้นที่ 6 ถึง 8**
พร้อมรายการข้อมูลที่ต้องจัดเก็บ

เหตุผลที่ถูกต้องคือ **ติดที่ขอบเขต**: งานตรวจสอบสินค้าอยู่หลังขั้นตอนการจัดส่งจากผู้ขายไปยังศูนย์ตรวจสอบ
ซึ่งเป็น Feature คนละตัวกับ ORDER และยังไม่มีในระบบเลย ต่อให้ได้ข้อสรุปเรื่องสิทธิ์ของ Inspector วันนี้
ก็ยังพัฒนาไม่ได้ เพราะ

- ยังไม่มีสถานะ Order หลัง `WAITING_SELLER_SHIP` ให้ผูกงานตรวจสอบเข้าไป
- ยังไม่มีตารางการรับของเข้าศูนย์และตารางผลการตรวจสอบให้เขียนผลลง
- ยังไม่มี Feature การจัดส่ง จึงไม่มีเหตุการณ์ที่ทำให้ Order เดินจาก "ผู้ขายจัดส่ง" ไปถึงศูนย์ตรวจสอบ

**ตัวปลดล็อกคือ Feature การจัดส่งและ Feature การตรวจสอบสินค้า ไม่ใช่มติเรื่องสิทธิ์ของ Inspector**

## 2. สิ่งที่ SRS ตอบไว้แล้ว (ไม่ต้องถกใหม่)

| หัวข้อ | ที่มา | สถานะ |
|---|---|---|
| หน้าที่ของ Inspector | **FR-15 ถึง FR-18** | กำหนดไว้แล้ว ให้ยึดตามต้นฉบับ |
| ลำดับงานตรวจสอบในกระบวนการหลัก | **ขั้นที่ 6 ถึง 8** | กำหนดไว้แล้ว (รับของเข้าศูนย์ → ตรวจสอบ → แจ้งผล) |
| รายการข้อมูลการรับสินค้าเข้าศูนย์ตรวจสอบ | SRS หัวข้อข้อมูลที่ต้องจัดเก็บ | กำหนดไว้แล้ว **ให้คัดลอกรายการฟิลด์จากต้นฉบับตอนเริ่มรอบนั้น** |
| รายการข้อมูลผลการตรวจสอบ | SRS หัวข้อข้อมูลที่ต้องจัดเก็บ | กำหนดไว้แล้ว **ให้คัดลอกรายการฟิลด์จากต้นฉบับตอนเริ่มรอบนั้น** |
| สถานะ Order ตลอดเส้นทาง | SRS (ดู `contract.md` หัวข้อ 2) | คัดมาไว้ใน Contract แล้วเป็นข้อมูลอ้างอิง |

เอกสารนี้ตั้งใจ **ไม่คัดลอกรายการฟิลด์มาไว้เอง** เพราะไฟล์ SRS ไม่ได้อยู่ใน repo
การคัดลอกมาโดยพิมพ์ตามความจำจะกลายเป็นข้อกำหนดปลอมที่แย่กว่าการไม่มีเลย
ให้เปิดต้นฉบับแล้วคัดลงเอกสารออกแบบของรอบนั้นตอนเริ่มงาน

## 3. คำถามที่ยังเปิดอยู่จริง (ตัดสินเมื่อถึงรอบนั้น)

**Inspector ควรเห็นข้อมูลผู้ซื้อและผู้ขายมากน้อยเพียงใด**

สิ่งที่มีอยู่แล้วให้ใช้เป็นจุดตั้งต้นของการตัดสิน
- ORDER-09 วางแบบแผนไว้แล้วว่า "มีสิทธิ์เข้าถึง แต่ระบบไม่แสดงอัตโนมัติ": ปิดบังเป็นค่าตั้งต้น
  ขอดูเต็มเป็น Endpoint แยกที่ต้องมีเหตุผลและถูกบันทึกลง `admin_access_logs` (ดู D-21, D-22)
- ตาราง `admin_access_logs` ออกแบบให้ใช้ซ้ำได้ เพิ่มค่าใน CHECK ของ `action`/`target_type` ก็พอ
- ข้อสังเกตเบื้องต้น: Inspector ต้องการ "ของชิ้นไหน ของ Order ไหน" เป็นหลัก ไม่ใช่ "ใครซื้อ"
  จึงน่าจะเห็นน้อยกว่า Admin แต่ข้อนี้ **ยังไม่ตัดสินในรอบนี้**

## 4. สิ่งที่รอบนี้เตรียมไว้ให้แล้ว

- สถานะ Order เพิ่มค่าใหม่ได้ด้วยการสลับ CHECK ตัวเดียว ไม่ต้องแก้ชนิดคอลัมน์
  (`String(32)`, ไม่ใช้ native enum ของ PostgreSQL — ดู `backend/app/models/order.py`)
- `uq_orders_active_product` ใช้เงื่อนไข `status <> 'CANCELLED'` จึงคลุมสถานะใหม่ให้เองอัตโนมัติ
- โค้ดฝั่ง Backend ตัดสินใจจาก **ชุดของสถานะ** (`PAYABLE_ORDER_STATUSES`, `CANCELLABLE_ORDER_STATUSES`)
  และตัดสินว่า "จ่ายแล้วหรือยัง" จาก `paid_at` ไม่ใช่จากชื่อสถานะ การเพิ่มสถานะจึงไม่ทำให้
  ใบเสร็จหาย ผู้ขายไม่เห็นที่อยู่ หรือปุ่มจ่ายเงินกลับมาเปิด
- แอปมือถือรองรับสถานะที่ยังไม่รู้จักแล้ว (แสดง "สถานะอื่น ๆ กรุณาอัปเดตแอปเพื่อดูรายละเอียด" แทนการพัง)
  แอปรุ่นเก่าจึงอยู่รอดตอน backend เพิ่มสถานะ
